4. Identity and isolation

How the system knows which agent did something, and why an agent can't fake it. Files: identity/, runtime/spawn.py, runtime/agent_template.py, runtime/isoprobe.py.

The problem

If an agent could sign as another agent, or read another's memory, "who did it" would be meaningless. Identity needs two things: keys the agent can't get and a process boundary the agent can't cross.

Keys (identity/keys.py)

  • Ed25519 keys for every principal: the gateway, monitor, operator, recovery, and each agent.
  • Private keys live in memory in the gateway process and never touch disk. Only the public keyring is written.
  • The witness makes its own key inside its own process.
  • Two key modes: fresh (random per run, the secure mode) and repro (derived with HKDF from a secret plus the seed, so a replay is byte-identical). Repro is explicitly not a security run.
  • verify_hex(pub, sig, data) never raises. It returns True or False.
derive_key_bytes(secret, seed, principal) =
    HKDF-SHA256(secret, salt=seed as 8 bytes, info=b"ks/key/v1/" + principal)

The signer service (identity/signer.py)

The agent holds no key, so it asks for a signature over a socket pair that only it and the gateway share.

agent process gateway process builds Envelope SignRequest{header} ───────────────► SignerService.handle checks: schema, current epoch, per-tick quota ◄─────────────── SignReply{sig} or SignRefusal{reason} sends SubmitFrame(envelope + sig) ───► Gateway.admit (verifies the signature again)
  • Each agent has its own path-less socket pair, so one agent can't reach another's signer.
  • signer_refusal() refuses if the agent's epoch isn't current or it has used its signing quota (MAX_SIGN_PER_TICK). A suspended agent can't even get new signatures.
  • A flood of signer lines is counted and dropped without a reply.

Process isolation (runtime/spawn.py)

  • Each agent runs as its own OS process under its own numeric uid: agents get 60001 and up (agent_uid), the witness gets 60000. This needs root inside the container (CAP_SETUID), which is why the Dockerfile uses USER root.
  • Processes are made non-dumpable (set_nondumpable), so another uid can't read their memory via ptrace or core dumps. They also get a clean environment and an adjusted OOM score.
  • Teardown kills processes by uid (kill_uids), so nothing survives a run.
  • runtime/isoprobe.py and setup.isolation_problems read back the real uids from /proc before tick 0. The system does not assume isolation happened. It checks, and records it in the Isolation object and the banner.
Degraded modeWithout per-agent uids (native macOS, or --shared-uid) attribution is declared VOID. The run still happens, but the banner and the verify report say isolation was degraded. Use Docker for the real demo.

The agent process (runtime/agent_template.py)

This is all that runs inside an agent process. It holds two sockets and nothing else: no keys, no paths, no record access.

  1. Read a TickFrame from the gateway: tick, epoch, and the view.
  2. Call the behaviour module's step(agent_id, seed, tick, view, sched), which returns an action or None.
  3. Build an Envelope: nonce from ks.rng, expiry_tick = tick + 2, current epoch.
  4. Send a SignRequest to the signer. If it replies SignRefusal, send a no-op.
  5. Send SubmitFrame (or NoopFrame) to the gateway, then read the ReplyFrame.

The behaviour is a pluggable module (--behaviour). For the world scenario, KS_FAULT is passed as an environment variable only to the culprit's process, so no other agent and not the gateway knows a fault is planned.

Connection binding

The barrier binds each connection to one agent (Gateway.bind, a 1:1 rule). A frame signed by agent B on agent A's connection fails with bad_sig. A frame on an unbound connection also fails. A system principal id on an agent connection is never verified.
