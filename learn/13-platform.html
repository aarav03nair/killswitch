The extension points

ToolDispatcher

classify(env) says R, C, I1, I2 or U. execute(env, txn) does the work, reading and writing only through txn. Implement this to expose your own tools.

ViewProvider

view(agent, tick, state) decides what each agent can see. Because views feed the read set, this is where dependency tracking comes from.

Policy

decide(env, class) returns None to admit, or a deny/hold verdict with a rule token.

Sensitive fields

A list in the run config (table.field). Each becomes its own versioned object so it can be reverted independently.

Detectors

Pure functions over a context. Add yours to the catalogue in monitor/detectors.py and declare the alert kind in the C4 contract.

Behaviour module

For agents: a module with step(...) loaded in the agent process. An LLM-backed agent would fit here (a stretch goal in HANDOFF).

Compensators

For class C tools: the registered opposite action the planner can run.

Outbox sinks

Destinations like payments and email. A real deployment adds a real delivery behind ks.dispatch.

A recipe: put a new system behind the gateway

  1. Model your data as objects. Pick object ids (table:pk), and list sensitive fields that should be reversible on their own.
  2. Write a dispatcher. One adapter per tool. Classify each as R, C, I1, I2. Anything unlisted is U and denied.
  3. Write the view. Decide what each role sees. Less is better: less read means less taint.
  4. Write the policy. Which roles may call which tools and write which tables.
  5. Write invariants. The things that must never be true of your data. Each becomes a detector.
  6. Register compensators for class C tools, and decide your hold window H.
  7. Run a fault drill. Make an inject spec for each failure you fear, with an oracle run to score against.

What would have to change for real deployments

Gaps between this and a product
  • Lockstep ticks. Real agents run asynchronously. The ordering and view-visibility rules (a write at tick t is visible at t+1) assume ticks. A real system needs an equivalent logical clock or sequence-based visibility.
  • State store. It is a SQLite store the gateway owns. Real systems have Postgres, S3, SaaS APIs and so on. You would need adapters that can supply before and after versions with hashes, or accept coarser guarantees.
  • Reads must be mediated. Dependency tracking only works if every read goes through the gateway's view or adapter. Reads that bypass it are invisible to taint.
  • Isolation. Per-agent uids inside a Docker container. In production you'd get this from separate containers, sandboxes or workload identities.
  • Irreversible effects. Outbox gating only works if the dispatch really happens behind the gateway.
  • LLM agents. The planner re-plans them with approval. There is no replay of a language model's behaviour.
  • Scale. Admission is sequential per tick and the code scans records in places. The project targets about 10 agents.

The mental model to keep

In one paragraphThe platform turns "agents doing things" into "a ledger of who read which versions and wrote which versions, signed and witnessed". Containment is a state change in that ledger (an epoch bump). Recovery is a query over it (taint closure), a diff of the plan against the store, and a set of recorded repair actions. Anything that can express its actions as reads and writes of versioned objects can sit behind it.
