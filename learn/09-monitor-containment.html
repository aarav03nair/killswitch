9. Monitor and containment

How a fault is noticed, pinned on an agent, and stopped. Files: monitor/, containment/, gateway/control.py.

Detect, then attribute (two separate steps)

The ruleDetectors find bad data and cite evidence. They never name anyone. A different module names the author, by lookup in the record. That's why attribution can't be fooled by what an agent says about itself.

Detectors (monitor/detectors.py)

Pure functions Context → list[Finding]. No LLM, no clock. A finding has evidence: record seqs and object versions.

DetectorLooks for

Whether an alert is hard or soft isn't decided in the detector. monitor/alerts.py takes it from the C4 contract table.

Attribution (monitor/attribute.py)

  • writers_of looks up which executed record wrote each evidence version, and returns the attributed agent. This is a write-set lookup.
  • root_candidates[0] is the sole writer of the evidence. A bounded backward walk over recorded read sets then ranks other agents that wrote what the writer read.
  • Agent-declared lineage and act_chain are never used (rule D8).
  • Read-reached agents are never auto-suspended. If two or more distinct writers share the evidence, or none, nobody is suspended. A human decides.
  • This is honest about collusion: it returns root candidates, not a verdict.

Containment (containment/__init__.py)

Containment.respond runs inside the same tick the fault was seen, before the next Gateway.open. For each alert it admits on c-0:

  1. One ks.alert record per alert, signed by ks.monitor and chained.
  2. For a hard alert with a decided target, one ks.control suspend record (auto=True, alert_id set, fresh strictly higher epoch).
Alert kindWho gets stopped
invariant (I-class), scopeThe attributed writer (root_candidates[0]) is auto-suspended.
signatureOnly the connection, not the agent.
reconcileNobody.
anomaly, rateAlert only (a human clicks).
tamper, witness_stallNobody is suspended, but recovery is frozen until a human looks (rule M12).

Why epochs make the kill switch reliable

before: crm epoch = 3 crm signs envelope with epoch 3 -> exec suspend: control record -> crm epoch = 4, status suspended after: crm envelope presigned at epoch 3 -> deny/stale_epoch crm envelope signed at epoch 4 -> deny/suspended (signer would refuse anyway) release: control record -> epoch = 5, status active old envelope at epoch 4 -> deny/stale_epoch

An agent that pre-signed a batch of actions before being suspended can't use them later, because their epoch is stale. The effect starts at the record seq of the suspend, and the step-13 re-read inside the transaction enforces it even for an action already in flight.

Human controls

release and revoke are operator actions (runtime/operator.py), via ks contain suspend|release|revoke|hold|unhold. Auto-suspend happens on hard evidence (bad signature, scope, tamper, I-class invariant). Anomalies get one click. Revocation is permanent and comes after confirmation.

What gets held when an agent is contained

  • The suspended agent's own future actions: denied.
  • Outbox items whose lineage touches tainted versions: held (lineage_hold). That is how bad data is stopped from leaving as a payment or email.
  • Independent agents: keep running.

Time-to-contain is measured from the records only. contain_times recomputes it from a run directory, and the scorer does the same.
