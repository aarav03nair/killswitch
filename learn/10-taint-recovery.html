10. Taint and recovery

How the system works out which work is damaged, and how it repairs only that. Files: taint/, recovery/, runtime/recover.py.

Taint: the blast radius

A version is (object, ver). The writer of a version is the executed record whose write set has it as after. Everything is built from the record, using hashes only (taint/closure.py).

  • Seed: the suspended agent's writes in its seed window (from the estimated start of the fault, t0, to its suspension). With no suspended suspect there is no seed and no plan (NoPlan).
  • Closure: follow the recorded read sets. An action that read a tainted version is tainted, and what it wrote is tainted in turn. Because read sets include the views delivered to agents, dependence is captured even if an agent never named its source.
  • Over-taint, don't under-taint. It deliberately errs towards flagging too much.
  • Repairs don't propagate. Records by ks.recovery are repairs (they re-write a clean value), so they don't spread taint.
  • Seed versions stop the walk. Record seq 1's versions are the clean baseline.
  • root_candidates runs a bounded backward walk (MAX_HOPS = 3) to rank who else could be the root.

The planner (recovery/planner.py)

Input: the chained records, a taint set, and optionally the live store (only to ask whether a restore source is redacted and what an outbox item's status is). It never reads fault or culprit. The suspect comes from the taint's suspect field.

Step order: cancel_outbox, restore, rerun, compensate, replan, flag.

Why cancel is used sparinglyCancelling an outbox item is irreversible, so the planner doesn't spend it until a person resolves the flag or approves the replan.

Dry run, approval, apply

  1. Dry-run (recovery/dryrun.py): execute the re-runs inside a rolled-back savepoint (Store.simulate), so nothing persists. Produce a diff showing what each step would change. Re-runs never re-emit effects because outbox idempotency keys dedupe them. If a re-run's simulated payload hash equals what was dispatched, the "dispatched_tainted" flag is dropped.
  2. Approval: a person approves the plan. The approval carries the plan_hash. If the plan changed since, the verdict is hold/stale_plan.
  3. Apply (runtime/recover.py): the gateway's RecoveryService executes each step as a ks.recover.<op> system envelope by ks.recovery, so recovery is itself recorded and verified (recovery_unbound if not tied to a plan).
  4. Restore uses expect: if the object's head is no longer the version the plan expected, the step is stale_plan instead of overwriting someone's newer write.
  5. Release: the operator unholds re-held clean items, which then pass the release phase.

Recovery is frozen (recovery_frozen) while verify fails or a tamper or witness-stall alert exists. You never repair on top of evidence you can't trust.

The honest limits

  • Irreversible effects that already left are compensated or reported, never "undone".
  • Language-model steps are re-planned, not replayed.
  • The culprit's honest work between the fault and its suspension is reverted, and counts as collateral loss (c_culprit_window), because the system never learns when the fault started.
