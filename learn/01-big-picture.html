One tick of time

Time is cut into ticks. The scheduler is the gateway itself (the barrier in runtime/barrier.py does the I/O). In every tick:

1 gateway.open(tick) release due outbox items, run control phase, build each agent's VIEW 2 barrier sends each agent a TickFrame {tick, epoch, view} 3 each agent decides an action from its view, asks the signer to sign it, sends SubmitFrame 4 gateway.tick(frames) admit frames in agent_id order (arrival order is thrown away) -> 14 checks -> run the tool in a DB transaction -> append a signed record 5 monitor looks at the new records; containment may suspend an agent 6 barrier pushes (seq, head hash, tick) to the witness, which signs a checkpoint
Key ideaAgents only see data through the view the gateway hands them, and every entry in that view is added to the action's recorded read set. That is how the system knows what each action depended on, without trusting the agent to say so.

A worked example: the bad IBAN

This is the hero scenario "F2+" in the code. The CRM agent writes a wrong bank account for a supplier, and other agents build on it.

  1. The fault. At the hero tick h, crm signs crm.update_supplier with an attacker IBAN. The gateway runs it and records write_set: supplier:S-22.iban v1→v2, author crm.
  2. Others read it. A tick later, billing's view includes the supplier row and the IBAN object, so billing's invoice record has that version in its read_set. Payments and comms then act on the invoice. The payment and email go into the outbox, with the lineage copied from the read set.
  3. Detect. The monitor's iban_checksum detector finds an invalid IBAN. It cites the object version as evidence.
  4. Attribute. A lookup finds which record wrote that version. Attributed agent: crm. No guessing.
  5. Contain. Containment records a ks.alert, then a ks.control suspend for crm with a fresh epoch. From that record on, crm's next request is deny/suspended. Outbox items whose lineage touches the tainted version are held.
  6. Recover. The planner restores the IBAN and the price to their last clean versions, re-runs billing/payments/comms on clean data, and flags what already left. A human approves after a dry-run. Triage's risk note stays, because it's a different object.
  7. Audit. ks verify re-checks the chain, signatures, witness checkpoints and more. ks score compares the final state with a "fault never happened" oracle run.

The design rules you will keep meeting

  • One mediated path. Nothing reaches state except through the gateway.
  • Evidence, not testimony. The gateway builds the read and write sets. A tool that lies about them is refused.
  • Rule 11: every envelope is recorded, including denials.
  • Rule 9: records hold hashes only. Raw values go in a side store, which can be redacted without breaking the chain.
  • Fail closed. An unknown tool is class U and is denied.
  • Deterministic. Same seed, same bytes, so a run can be replayed and compared.
