5. The tick barrier (runtime)

runtime/ is the engine room. It starts everything, moves time forward in lockstep, and never decides anything about the content of a request.

Why ticks?

Real agents run at different speeds, so the order of actions would depend on timing. That would make runs impossible to replay and the evidence hard to reason about. Instead, the gateway acts as a scheduler: nothing happens between ticks, and within a tick the gateway sorts frames by agent id. Same seed, same behaviour, same bytes.

The loop (runtime/barrier.py)

open Gateway.open(tick, agents) -> TickFrame per agent -> send collect one frame per connection: FIFO reads, deadline, and signer requests handled meanwhile decide Gateway.tick(tick, [InFrame]) -> [(conn_id, ReplyFrame)] reply send replies cleanup K-miss / oversize close witness push (seq, head, tick) to the witness, wait for the signed checkpoint
The boundaryThe barrier only looks at frame length and terminator, never inside a frame. Everything that decides (control, view, admission, dispatch, monitor) lives behind Gateway.open and Gateway.tick. This keeps I/O bugs out of the decision logic.

Misbehaving connections

SituationWhat happens
Agent misses the deadlineAfter MAX_MISSES = 3 in a row the connection gets EOF. This is an anomaly, never a suspend.
Oversize frameThe connection is closed (max frame size is a contract constant).
Outbound queue over 64 KBEOF (OUT_QUEUE_CAP).
8 recorded denials in one tickThe gateway flood-suspends the connection (FLOOD_K = 8), recording one control. Extra frames are dropped and counted.
Witness doesn't acknowledgeA stall. The monitor has a witness_stall detector.

The other runtime files

FileJob
run.pyThe wiring point for ks run: builds config and keys, spawns the witness and agents, builds the Gateway with its store, policy, control and outbox, drives the barrier, tears down, prints the RunAnchor. It is the only place world is connected to gateway.
setup.pyResolves the scenario (skeleton or the 10-agent world), picks the dispatcher, checks isolation, refuses an existing run dir.
options.pyThe run options (agents, ticks, seed, key mode, deadline, pause points, fault, rogue).
operator.pyA local socket for the human operator, authenticated by peer credentials. Turns requests (suspend, release, unhold, resume) into ks.operator-signed envelopes on c-0.
recover.pyThe gateway-side RecoveryService that applies recovery plans (page 10).
rogue.pySupport for the jury's "run arbitrary code inside a rogue agent" test.

The RunAnchor

At the end, ks run prints a RunAnchor: the final chain head plus hashes of config and keyring. You keep it outside the run directory. ks verify --head ANCHOR uses it to prove nothing was truncated or swapped. Without an anchor, the record is only tamper-evident up to the last witnessed checkpoint.
