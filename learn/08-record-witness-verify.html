8. Record, witness, verify

How the audit trail is built, why a cheating agent (or even a bug in our own writer) can't quietly rewrite it, and how anyone can check it later. Files: recorder/, witness/, verify/.

Three layers of evidence

layer 1 hash chain each record contains the hash of the previous one layer 2 gateway signature each record is signed by the gateway key (gw_sig) layer 3 witness a separate process signs (seq, head, tick, count) every tick

Each layer closes a gap the previous one leaves. A chain alone can be rebuilt by someone who edits history and recomputes every hash. A gateway signature alone can be forged if the gateway's writer is compromised. A witness in a different process, with a different key, holds an independent copy of "the head was X at tick T".

The recorder (recorder/__init__.py)

  • Only the gateway process holds a Recorder.
  • begin() reserves the next seq (one open reservation at a time). The state transaction writes under that seq.
  • append() builds Record.seal(prev_hash=head, seq, record_id, ...), signs it with the in-memory gateway key, and writes it to record.jsonl.
  • rollback() releases a reservation if state was rolled back, so the record has no gaps.
  • If an append fails after state was committed, the recorder aborts for good (RecorderAborted). It never retries or reuses the seq. Verify then reports RECONCILE.
  • put_side(domain, hash, value) files raw args, results and raw frames in the side store (idempotent).
Rule 9Records hold hashes, not values. A person's data can be redacted from the side store without breaking the chain, because the chain only ever contained the hash.

The witness (witness/)

  • A separate process, uid 60000, with its own key and its own files. It starts from a non-dumpable bootstrap and receives pre-opened file descriptors, so it doesn't need paths.
  • Each tick the barrier pushes (seq, head, tick) through WitnessLink.push. The witness signs a WitnessCheckpoint(seq, head, tick, count) and appends it to witness.jsonl.
  • It never reads record.jsonl. It only signs what it is pushed, and it won't sign a head that regresses or conflicts with an earlier one. At most one checkpoint per tick; count rises by exactly 1 per line.
  • If the witness doesn't acknowledge, the gateway sees a stall.

Verify (verify/core.py)

ks verify RUN [--head ANCHOR] runs offline and stops at the first failure, in this order:

  1. IO: config, keys and record files parse.
  2. Anchor hashes: keyring and config match the anchor, before any signature is trusted.
  3. Keyring complete.
  4. Record pass: parse, seq continuity, prev_hash, hash, gw_sig, each agent signature against sig_ok, and the seed rule (ks.seed at seq 1).
  5. Witness pass: witness signature, count chain, truncation, heads match record hashes.
  6. Anchor vs last checkpoint: if you passed --head, it must match.

Then more passes:

PassCatches
Dispatch window (F4, window_violation)An effect dispatched early, or despite a hold, taint or suspension.
Alerts cross-check (F6, alert_mismatch)alerts.jsonl differing from the chained ks.alert records.
Side store (side_entry_mismatch)A side file whose content doesn't hash to its name.
Recovery binding (recovery_unbound)A recovery action not tied to an approved plan.
reexec_passRe-executions that don't match their hold.

The report ends with a VerifyReport JSON line (exit, anchored, isolation, first_bad if any). The demo script asserts exit == 0, anchored == true and the isolation mode.

Decision replay (verify/decisions.py)

ks run --decisions SRC replays the human operator's controls from an earlier run. It refuses a source with no anchor, with repro keys, or that fails verify --head. Only ks.operator-signed, executed controls are replayed. Any difference between the replay and the source is a replay_mismatch. This lets you re-run an incident with the same human decisions and check the machine did the same thing.

What it does and doesn't promise

  • Tamper-evident, up to the last witnessed checkpoint. An edit or truncation is detected. With an anchor kept outside the run directory, truncation after the last checkpoint is detected too.
  • It is not "tamper-proof". It doesn't stop someone changing files, it makes the change visible.
  • Per-agent attribution relies on uid isolation. If that failed, the report says so.
