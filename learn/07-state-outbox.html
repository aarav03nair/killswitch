7. State store and outbox

Where the data lives, why every old version is kept, and how irreversible effects (payments, emails) are held back until they are safe. Files: state/, gateway/outbox.py.

The versioned store (state/store.py)

A SQLite database, state.db, used only by the gateway. It never overwrites. It appends versions.

TableHolds
objectsThe current head of each object: obj, head_ver, head_hash, head_value, head_redacted.
versionsEvery version ever written: (obj, ver, hash, author, seq, action_id). Append-only: SQL triggers abort any UPDATE or DELETE.
sideRaw values by hash, with a redacted flag.
metaSettings such as the sensitive-field list.
  • Each version records its author and the record seq that wrote it. That is the join between state and evidence.
  • The hash is of the value, so a later read can say "I read this exact version".
  • Reconciliation: state_digest over the live store should equal the digest of folding the record. If they differ, verify says RECONCILE.
  • Savepoints and simulate let the recovery dry-run execute re-runs inside a transaction that is always rolled back, with transaction-control SQL blocked so simulated code can't commit.
  • A tombstone hash represents "object deleted" or "didn't exist before".

Objects, rows and sensitive fields (state/fields.py)

Object ids look like suppliers:S-22 (a row) or suppliers:S-22.iban (a field object). Config lists sensitive_fields such as suppliers.iban. For those fields:

  • The field is its own versioned object, and the row's value no longer contains it.
  • A read of the whole row lists the row and its field objects.
Why this mattersIf the IBAN lives inside the supplier row, reverting the IBAN means reverting the row, which would also erase triage's unrelated risk note. As a separate object, the IBAN can be restored alone and the note survives. That is the "triage's note is kept" line in the abstract. Sensitivity comes only from config; there is no IBAN-specific code in the store.

Views (the read side)

Agents don't query the store. At Gateway.open, the ViewProvider (the world's build_view) produces each agent's per-tick view from a snapshot that excludes this tick's writes. Every view entry is added to the read set of whatever the agent does that tick. Scope per role is in world/scenario.py (SCOPES) and enforced as the read scope in the policy.

The outbox (gateway/outbox.py)

Some effects can't be undone: a payment, an email. The outbox makes them two-step. A tool never sends anything. It returns an OutboxRequest(sink, class, payload).

Creating an item

Inside the same transaction and the same record as the action, the gateway creates an object outbox:ob-NNNNNN (a C3 OutboxItem). The gateway derives everything a tool must not choose:

  • the id and the idempotency key (idempotency_key(agent, action, sink, n)), so a re-run never sends the same effect twice
  • the lineage: the record's read set (never what the agent declares)
  • the release tick: tick + H where H = hold_window_ticks
release_tick = tick + H
release_tick = max(tick + H, v + 2H)    # if lineage holds a sensitive-field version written at tick v

Status lifecycle

queued ──► released? ──► dispatched (a signed ks.dispatch record; the effect leaves) │ ├──► held (lineage touches a tainted version, or a sensitive field changed) │ └─ unhold ─► queued again (re-checked at the next release phase) └──► cancelled (recovery or operator)

The release phase

At the start of each tick, for each due item in id order:

ConditionResult
Author is suspended or revokedStays queued, no record. Leaves only after a release.
Lineage touches a tainted versionks.control hold, reason lineage_hold
A sensitive-field version in the lineage is no longer the headHold, reason sensitive_field
Otherwiseks.dispatch

Every outcome is a signed gateway envelope on c-0 whose write set is the status change, so a refusal to dispatch is itself recorded. ks verify then checks the dispatch window (F4): each dispatched item must have been released no earlier than its release tick, with no unlifted hold, taint seed or author suspension in between.

The hold windowH is the grace period. With H=0 an item is released the next tick, with H>0 there is time for the monitor to react before money moves. The benchmark compares both (--hold 0,6). The honest cost of holding is measured as "collateral stall".
