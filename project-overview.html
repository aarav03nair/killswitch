Project Kill Switch

A black box and an off switch for networks of AI agents: find out what broke, who broke it, contain it, and undo only that damage.

SEED Hackathon 2026 · Sub-theme 03 “The Kill Switch” (Agent Safety)

1. The problem

“Ten agents are working. One just broke something.”
You need to know what changed, who changed it, and how fast it can be undone, without throwing away everyone else’s good work.

Logs are testimony

An agent’s own log is self-reported. It can be wrong, incomplete or forged.

Kill switches are blunt

Existing controls stop one agent or all of them. They don’t repair work already done.

Undo is a dependency problem

Once other agents have read a bad write, restoring a snapshot erases their valid work too.

2. What we are building

A gateway that sits between agents and shared state. Agents can only act through it. It turns every action into signed, tamper-evident evidence, and uses that evidence to identify, contain and recover.

Without it

  • Bad write lands; nobody knows which agent
  • Others read it and build on it
  • Fix = restore a snapshot, losing good work

With it

  • Every action is signed with the agent’s identity
  • Read and write sets show exactly who touched what
  • Only the culprit’s damage and its downstream readers are reverted

3. How it works

1 IdentityEvery action signed per agent
2 GatewaySingle mediated path to state
3 RecordHash-chained, read/write sets
4 WitnessSeparate process checkpoints the chain
5 MonitorDetect via data invariants, attribute by lookup
6 ContainSuspend agent, hold tainted outputs
7 RecoverTaint-scoped revert, re-run or flag
8 Verifyks verify checks it offline

Each agent runs under its own OS user id inside a Docker container, so agents can’t read each other’s memory or touch the witness. The whole run is deterministic from a seed, so results can be replayed and audited.

4. How we map to the judging criteria

Judges look atOur answer
Time to identify
How fast can we say what broke and which agent did it?		 Every action an agent takes goes through our gateway, which stamps it with that agent’s signature and writes down exactly what it read and what it changed. When something goes wrong, finding the culprit is just a search through that record. We never ask an AI to guess, and we never trust what an agent says about itself. Research shows AI guessing the guilty agent is right only about half the time.
Time to contain
How fast can we stop the damage from spreading?		 A monitor watches the data for things that should never happen (for example, a payment going to an account that doesn’t match). When it fires, we stop only the bad agent, in steps: pause it, then fully cut off its access. Any outgoing action that depends on its bad data, like an email or a payment, is held until a person checks it. The other nine agents keep working the whole time.
Clean recovery
Can we undo the damage without losing good work?		 We follow the trail: which data did the bad agent write, and which other agents read it afterwards? Only that chain of affected work is rolled back or redone. Everything else stays untouched. We then score the result against a known “correct” outcome with two numbers: how much damage we fixed, and how much good work we accidentally lost. We compare that with simply restoring a backup, which throws away everyone’s work.
Auditable, not just demoed
Would it still hold up if someone tries to break it?		 The record is a chain where every entry locks in the one before it, so editing history leaves visible damage. A separate witness program keeps its own copy of the latest checkpoint, so even a cheating agent can’t quietly rewrite the past. Anyone can run ks verify afterwards, offline, to check the record is intact. We also wrote down the attacks we expect and plan to try them ourselves before the jury does.
Framing
How we explain the problem to the jury.		 We start from one idea: every change has an author, and every read has a source. Once you record that, the three hard questions (who did it, how do we stop it, how do we undo it) become three simple look-ups on the same record. That gives the jury one clear story instead of three separate tools.

5. Code map

src/ks/contracts

The shared rulebook. It defines what every message, record and report looks like, and writes data in one fixed format so that the same input always produces the same fingerprint. Every other part depends on it.

gateway and runtime

Gateway: the security guard. Every agent action must pass through it to be checked and carried out. Runtime: the engine room. It starts each agent as a separate process under its own user, and moves everyone forward one step at a time so runs are repeatable.

identity, recorder, witness

Identity: creates keys and signs actions, so agents never hold their own keys. Recorder: the logbook, with each entry locked to the one before it. Witness: a separate program that keeps its own checkpoints, so the logbook can’t be quietly rewritten.

state and taint

State: the shared data the agents work on. It keeps every old version, which is what makes undo possible. Taint: works out the blast radius. Starting from a bad write, it finds every later piece of work that depended on it.

monitor, policy, inject

Monitor: watches for data that breaks the rules, names the agent responsible and raises alerts. Policy: the rules for what agents may do. Inject: deliberately causes a failure so we can test that the system catches it.

world, verify, cli

World: the pretend company with 10 agents that we test on. Verify: the auditor. It re-checks a finished run for tampering without needing the system to be running. CLI: the ks command you type to run and verify.

Also: tests/ (per-module tests and a red-team spec), org/ (charter, design decisions, threat model, issues), research/, abstract/ (submission support kit).

7. Beyond the hackathon

The core is domain-neutral: the gateway calls a pluggable tool-dispatcher interface, and the record, witness, verify and taint modules know nothing about banking. As a product it is a flight recorder and selective undo layer for any team running multiple agents on shared systems, which matters most in regulated industries that need audit trails (EU AI Act Art 12/14, RBI FREE-AI).

Honest limits: we do not reverse irreversible external effects such as sent emails or payments (they are compensated or reported), we make no “tamper-proof” claim (the record is tamper-evident), and strong isolation requires the Docker container.
